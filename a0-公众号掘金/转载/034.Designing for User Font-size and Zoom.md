今年早些时候，我提出了一些关于如何在现代CSS中处理流体网页排版的问题。但恐怕我混淆了几个问题，也没有提出任何有用的替代方案。现在我想深入研究，理清思路，寻找解决方案。

第一篇文章围绕*流体排版*展开——字体大小和比例适应视口——但我在这里主要关心的与流动性无关。

所有主流浏览器都提供`16px`的默认字体大小，作为每个网站构建的基础。用户可以通过设置全局字体大小偏好来更改该值，该设置将应用于他们访问的每个网站。CSS作者可以选择使用或忽略该设置，然后用户可以根据需要对特定网站进行页面缩放调整。我想深入探讨所有这些步骤，并考虑现代CSS如何让我们改进继承的最佳实践。

## 融合作者和用户偏好

对我的眼睛来说，在我的笔记本电脑上，大约`20px`的字体大小比`16px`的浏览器默认值感觉更好。所以在我看来，我应该将用户偏好设置为`20px`，这个更改应该会改善我的网络体验。

我不期望所有内容都能看到* exactly* `20px`的字体——我也不想这样！

- **并非所有内容都有相同的需求**。当我阅读博客文章时，我喜欢较大的文本，但当我填写电子表格时，较小的文本更有意义——只要我还能阅读它。没有一种偏好设置能在两种情况下都完美适应。
- **所有样式都是上下文相关的**，我们关心的是整体效果。我的`16px`默认大小会根据使用的字体、可用空间、配色方案、行长度、空白等因素而有所不同。
- **流体类型（根据定义）是动态值**。如果我们以后想集成视口单位，就不能同时*完全*匹配用户偏好。

因此，全局偏好是有限的，永远不会提供完美的解决方案。我们需要某种方式让作者调整这些偏好，使其更适合特定上下文，以及让用户可以在逐个站点的基础上进行最终调整的页面缩放选项。

但全局设置应该有*意义*，理想情况下，它是用户愿意更改以匹配其*实际偏好*的值。因此，作为作者，我们的问题是如何最好地解释和调整该偏好，使其在我们构建的网站上有用，即使它没有被*直接*应用。

### 当前方法是相乘

当前的最佳实践是先选择我们喜欢的理想像素字体大小，然后通过假设`1em = 16px`（浏览器提供的常见默认值）将其转换为`em`或`rem`。结果可以通过`em`应用于`html`元素，或通过`rem`应用于`body`标签。通常，这种转换是在第三方工具中完成的，但我们也可以在CSS中明确地进行计算：

```css
html {
  /* 这应该适用于像素单位，但浏览器尚未支持 */
  --DEFAULT: 16;
  --ideal: 24;

  /* calc(24 / 16 * 1rem) */
  font-size: calc(var(--ideal) / var(--DEFAULT) * 1em);
}
```

使用这种方法，我们实现了两个重要目标：

1. 我们（作为作者）可以为网站内容选择理想的基准大小（在这种情况下是去掉单位的`24px`），它将适用于大多数从未更改默认设置的用户。
2. 当用户更改字体大小偏好时，我们的网站文本会相对于该偏好放大或缩小。
3. 用户在进入页面后，还可以使用内置的浏览器缩放工具进行放大或缩小。

我们有能力建立一个设计，用户也有能力调整它——既可以通过即时/本地缩放，也可以通过长期/全局偏好。这听起来是一个不错的解决方案！

但是，如果网站设计师喜欢`24px`的字体，而我（作为用户）也请求`24px`的默认值，我们应该达成一致，对吧？相反，上面的方法会给我们一个`1.5em`的基准大小（`24 / 16 * 1em`），结果是（`1.5 * 24`）`36px`的字体。

这种调整有帮助吗？这不是设计师想要的字体大小，也不是我作为用户要求的字体大小，更不是在某种有意义的方式下适应上下文的字体大小。我们没有融合我们的风格偏好来找到最佳契合点，而是*将它们相乘*。

这不是世界末日，但它足够大，以至于每次我访问一个本应完美适合我的页面时，我都需要缩小。通过设置偏好，我让一个以前适合我需求的网站变得*不那么可读*。这让我非常犹豫是否要设置字体大小偏好。考虑到这个结果，我并不惊讶很少有人更改他们的默认设置。

不过，这比简单地覆盖或丢弃用户偏好要好得多。如果我需要，它确实允许我有一些输入，而且我可以即时进行调整。这不是一个*糟糕*的解决方案——在一段时间内，它可能是我们能做的最好的。但它也不是一个*很好*的解决方案，我认为我们可以做得更好。

### 替代方案1——信任用户

如果我们不需要控制字体大小，不设置字体大小也没关系！Adrian Roselli将此称为*[每个人都保守的终极理想最佳基准字体大小秘密](https://adrianroselli.com/2024/03/the-ultimate-ideal-bestest-base-font-size-that-everyone-is-keeping-a-secret-especially-chet.html)*。我同意，如果网络的更多部分是围绕用户偏好构建的，那将是理想的。我也认为在许多情况下，`16px`作为默认值*太小*——但这不是问题。在一个大多数网站尊重我偏好的世界里，我只需更改我的偏好就能得到我想要的结果！

但这不是我们生活的世界，也没有考虑到设计师的专业知识，以帮助将我们的偏好适应不同的上下文。所以也许我们可以找到一个折中的解决方案。

### 替代方案2——协商平均值

在*级联HTML样式表*的原始提案中，Håkon Lie提出了一种通过加权平均值来平衡用户和作者之间所有样式冲突的方法。声明可以用百分比*影响力*标记，用户首先获得优先权来声明影响力，作者则分配剩余的影响力。如果用户声称`100%`的影响力，他们的样式将被使用而不进行调整。但如果他们声称`60%`的影响力，那么作者也可以用剩余的`40%`发表意见。最终结果将是两种样式的平均值，`60%`权重偏向用户样式：

```css
/* user.css */
html {
  /* 20px字体大小，60%影响力 */
  font-size: 24px 60%;
}

/* site.css */
html {
  /* 20px字体大小，60%影响力 */
  font-size: 18px 40%;
}

/* 结果：21.6px */
html {
  font-size: calc((24px * 0.6) + (18px * 0.4));
}
```

提案的这一部分后来被简化为二进制的`0%`（默认）和`100%`（使用`!important`），所以我们不再有办法向用户请求加权平衡——但我们仍然可以提供平均值。这里的用户偏好由`1em`表示，而像素值表示我们的网站设计：

```css
html {
  font-size: calc((1em + 24px) / 2);
}
```

这个计算给了我们平等的影响力，但我们也可以根据设计目标调整权重。这里有一个 playground，可以尝试不同的用户和站点设置，以及不同的权重：

[CodePen演示](https://codepen.io/miriamsuzanne/embed/QwjywYj?height=600&amp;slug-hash=QwjywYj&amp;default-tab=result&amp;user=miriamsuzanne&amp;name=cp_embed_1)

在某些方面，我认为这是理想的解决方案——它同时考虑了网站设计和用户偏好，并在它们之间找到了中间立场。但在默认情况下，当没有给出明确偏好时，浏览器提供的`16px`被赋予了很多（不应有的？）权威。我也想象网站作者不会对一个*几乎从不*返回他们为设计选择的值的解决方案感到满意。

当我们不愿意自己忍受缺乏精确控制时，却要求用户忍受，这是不是很讽刺？我想，这就是所谓的*以用户为中心的设计*吧？哦，好吧，让我们尝试另一种方法。

### 替代方案3——较大值获胜

与其将默认设置视为*首选*文本大小，我们不如将其视为*首选最小值*。我想有些情况下这种假设会失败，但根据我的经验，它更接近人们使用字体大小偏好的方式。

使用CSS中的`max()`函数，我们可以将网站字体大小设置为*精确*使用，除非用户请求了更大的字体：

```css
html {
  /* 用户偏好和网站设计中的较大值 */
  font-size: max(1em, 20px);
}
```

这只允许用户偏好增加我们的网站字体大小。如果我们也想允许减小默认值，可以切换到`clamp()`函数。这个解决方案优先考虑网站大小，同时将我们选择的值限制在*接近*用户偏好的范围内：

```css
html {
  /* 设计偏好，限制在不偏离太远的范围内 */
  font-size: clamp(1em, 20px, 1.25em);
}
```

这些最小值和最大值不是为了达到特定大小而设计的——这里的`1em`是`16px`还是`25px`并不重要，我们也没有进行单位转换来得出这些数字。目标只是让我们在两端都*接近用户偏好*，有足够的回旋余地在默认情况下得到我们选择的输出。我们可以通过将最小值或最大值移近或远离用户的首选`1em`来调整范围的紧密程度。

只要我们的理想字体大小在范围内，我们就坚持使用我们带来的大小。但如果用户偏好超出了该范围，字体大小将进行缩放以适应。这里的`14px`偏好会稍微缩小，`20px`设置不需要放大，但更大的偏好将完全覆盖我们。

### 我们正在协商而不是相乘！

这些折中的方法都没有试图给用户* exactly*他们请求的字体大小。相反，它们是试图重新思考网站设计如何最好地考虑用户偏好的*变化*。对我来说，这两种方法都感觉是改进，因为它们协商了某种平衡，而不是结合我们的整体偏移量。

今天早上，[Sondra](https://www.oddbird.net/authors/sondra/)开玩笑说，我们的[当前团队](https://www.oddbird.net/about/)在OddBird工作的时间*加起来有67年*——[James](https://www.oddbird.net/authors/james/)指出，这比NASA还老！这个数字准确地说明了每个人以及我们在团队中的每一年——但简单地将所有值相加并不能给我们一个有意义的结果。更有用的说法是，我们在团队中的*平均时间是8年*，*我们大多数人*在团队中的时间*超过5年*。最小值约为1年，但[Jonny](https://www.oddbird.net/authors/jonny/)和我已经一起做了17年了！

在我看来，当前的字体大小最佳实践导致了类似的荒谬的"组合偏好"计算，更有用的是考虑平均值和范围。

作为一个优势，这些方法将任何px到rem的转换留给浏览器来解决——而不是我们需要预处理的计算。如果我们有一个（静态）像素值作为目标，那就是我们提供的值。

同时，`em`值在任何大小下都*相对于*用户偏好。与其将`2em`视为可能的`32px`输出，我更愿意将其视为带有变量和回退的数学方程：`2 * var(--user-preference, 16px)`。当我关心*关系*时，我使用`em`；当我关心*实际大小*时，我使用`px`。对我来说，这是CSS中单位的基本规则——我们应该说我们的意思。

### 我们可以在这里使用`px`值吗？

我们通常被告知不要以像素为单位设置字体大小，因为这会覆盖用户偏好。但在这里，`max()`比较仍然允许我们的用户在*离他们的偏好太远*时覆盖我们的静态`px`值。据我所知，这消除了字体大小中`px`值的问题。

我已经开始在新项目的`html`上使用`max()`方法来处理用户和站点默认值的合并。从那里，我可以使用[Utopia.fyi](https://utopia.fyi/)（或类似工具）在`body`上生成基于协商默认值的流体比例。我遇到的唯一问题是，我现在需要Utopia停止为我进行`em`转换。但我会在关于*使其全部流体化*的下一篇文章中详细讨论这个问题。

## 附言——仅文本缩放

由于全局字体大小偏好是有限的，快速调整的能力至关重要。无论我的浏览器偏好如何，我访问的一些页面都需要放大或缩小才能很好地工作。

这种调整通常需要浏览器UI——页面缩放（大多数浏览器都提供）和仅文本缩放（仅在一些浏览器中提供）的某种组合。页面缩放通过*改变像素大小*来使所有内容同时缩放，而仅文本缩放只调整字体大小，不改变其他任何内容。

我听到很多人建议，仅文本缩放会更有用——如果浏览器将其设为默认值的话。Richard Rutter在[他对我上一篇文章的回复](https://clagnut.com/blog/2441/)中也提到了这一点。我同意，*大多数时候*我只需要为文本可读性而缩放，而不需要整个布局——包括空白和图像——以相同的速率缩放。

但我不认为浏览器可以独自解决这个问题。事实上，我期望浏览器在这方面*跟随我们的领导*。[Safari](https://support.apple.com/en-gb/HT207209)和[Firefox](https://support.mozilla.org/en-US/kb/font-size-and-zoom-increase-size-of-web-pages#w_how-to-only-change-the-size-of-the-text)都支持仅文本缩放。Firefox需要更改设置，但Safari有一个快捷键——在使用command-plus/-minus缩放时按住option键。这里有一个[测试页面](https://cdpn.io/pen/debug/JodmKKp)，你可以用来看看区别：

[CodePen演示](https://codepen.io/miriamsuzanne/embed/JodmKKp?height=600&amp;slug-hash=JodmKKp&amp;default-tab=result&amp;user=miriamsuzanne&amp;name=cp_embed_2)

请注意，如果您为基于`em`的布局切换开关，页面缩放和仅文本缩放的行为是相同的（缩放所有内容）。大多数响应式网站也是如此，包括OddBird网站、[我的个人网站](https://miriamsuzanne.com/)和[Richard的网站](https://clagnut.com/)。

响应式网页设计严重依赖相对大小，所以我们都做出这个选择是有意义的。历史上，在同一个布局中混合流体和固定方面要困难得多。但即使是现在，它也能保持简单，并*按比例*调整所有内容的大小以适应文本。一段代码可以同时支持放大和小屏幕布局。

我不知道这有多重要。也许这也是我们需要重新考虑的最佳实践——停止使用完全字体相对单位构建我们的网站？或者也许保持现状就好。
但除非我们改变构建响应式网站的方式，否则我认为浏览器没有太多理由优先考虑仅文本缩放。
