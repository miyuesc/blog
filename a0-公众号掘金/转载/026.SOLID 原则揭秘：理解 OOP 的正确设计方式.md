# Introduction

Whether you’re building a small script or architecting a large-scale application, how you structure your code today determines how easy it is to adapt tomorrow. That’s where the **SOLID principles** come in.

This principle is introduced by **Robert C. Martin (Uncle Bob).** If you follow these principles while writing your application, your code will **not** become a mess when it grows very large, and it will be very easy for you to add new features to it.

When it comes to SOLID principles, there are a lot of misconceptions and misunderstandings among developers, but I can guarantee you, after reading this blog, you will not have any confusion, and you can also apply it in real-life coding.

We will be using **Typescript** for code snippets. Concepts are more important; code can be done in any language, but still, you don’t want to read typescript, then you can convert the code snippets in your preferred programming language with ChatGPT.

Full Form of the SOLID principle:

- **S:** Single Responsibility Principle (SRP)
- **O:** Open/Closed Principle (OCP)
- **L:** Liskov Substitution Principle (LSP)
- **I:** Interface Segregation Principle (ISP)
- **D:** Dependency Inversion Principle (DIP)

# Single Responsibility Principle (SRP)

Definition: *A class should have only one reason to change.*

Means a class should have only those methods which only change for a single reason or are impacted by only one source.
Simply put, if in future you want to modify the code of a class, then you should only touch that class code every time because of a single source.

With the definition, we couldn’t understand anything, so let's take many examples to make it clear.

```typescript
class TicketBooking {
  constructor(
    private movieId: number,
    private userId: number,
    private seatNumber: string
  ) {}

  checkSeatAvailability(): boolean {
    // Logic to check seat in DB
    return true;
  }

  calculatePrice(): number {
    // Price logic based on seat type, timing
    return 300;
  }

  makePayment(): boolean {
    // Call payment gateway API
    return true;
  }

  sendConfirmation(): void {
    // Send SMS or Email
  }

  book(): void {
    if (this.checkSeatAvailability()) {
      const price = this.calculatePrice();
      const paid = this.makePayment();
      if (paid) {
        this.sendConfirmation();
        console.log('Booking successful!');
      }
    }
  }
}
```

The above code violates SRP because it has 4 logical reasons to change:

- Seat checking logic changes
- Price policy
- Payment gateway
- Notification/confirmation logic changes

Payment and price are handled by different teams, so if tomorrow, when the payment method changes or the price policy changes, you need to modify the TicketBooking class. There are 4 sources that can change the code of this class, so this violates SRP.
One class should only change due to one source.

To correct the above code, we need to split it into multiple classes where each class can only be changed due to a single source or reason.

```typescript
class SeatChecker {
  isSeatAvailable(movieId: number, seatNumber: string): boolean {
    // Check in DB if seat is free
    return true;
  }
}
class PriceCalculator {
  getPrice(movieId: number, seatNumber: string): number {
    // Logic based on seat type, timing, etc.
    return 300;
  }
}
class PaymentService {
  pay(userId: number, amount: number): boolean {
    // Payment gateway integration
    console.log(`Processing payment of ₹${amount} for user ${userId}`);
    return true;
  }
}
class Notifier {
  sendConfirmation(userId: number, movieId: number): void {
    // Send email/SMS
    console.log(`Confirmation sent to user ${userId} for movie ${movieId}`);
  }
}
```

Now, the TicketingBooking class coordinates everything

```typescript
class TicketBooking {
  constructor(
    private seatChecker: SeatChecker,
    private priceCalculator: PriceCalculator,
    private paymentService: PaymentService,
    private notifier: Notifier
  ) {}

  bookTicket(userId: number, movieId: number, seatNumber: string) {
    if (this.seatChecker.isSeatAvailable(movieId, seatNumber)) {
      const price = this.priceCalculator.getPrice(movieId, seatNumber);
      const paid = this.paymentService.pay(userId, price);
      if (paid) {
        this.notifier.sendConfirmation(userId, movieId);
        console.log("Booking successful!");
      } else {
        console.log("Payment failed!");
      }
    } else {
      console.log("Seat not available!");
    }
  }
}
```

Most people confuse SRP by thinking that a class should only contain one method, but that’s wrong. It can have multiple methods.
Some people think SRP, like a class, handles only a single thing. But thinking like that is very confusing.

So just remember that SRP means a class should only contain that set of methods which change in future or do any code inside that class in future due to a single source or reason.

# Open/Closed Principle (OCP)

Definition: *Software entities (classes, modules, functions) should be open for extension, but closed for modification.*

## What does it actually mean?

- **Open for extension** → you can add new functionality
- **Closed for modification** → you should not change existing tested code to do it

**Goal:** Add new features without breaking existing logic

See the below code:

```typescript
class PaymentProcessor {
  process(paymentMethod: string): void {
    if (paymentMethod === "credit_card") {
      console.log("Processing credit card payment...");
    } else if (paymentMethod === "paypal") {
      console.log("Processing PayPal payment...");
    } else if (paymentMethod === "upi") {
      console.log("Processing UPI payment...");
    } else {
      throw new Error("Unsupported payment method");
    }
  }
}
```

Above code violates OCP because:
Every time a new method (like Stripe, Crypto Pay) is added, you have to:

- Modify this class
- Risk of breaking existing code
- Add more `if-else`

It is neither scalable nor maintainable.

To fix it, we have to make the code such that there is no need to change the code of the class PaymentProcessor (closed for modification), and still add new payment methods in the future (open for extension).

Instead of writing the implementation of every payment method in PaymentProcessor classes, we should accept an “interface” and call the method of the interface.
When calling the class we should provide concrete implementation according to our need of whichever payment method we want.
Below is the refactored code:

```typescript
interface PaymentStrategy {
  pay(): void;
}

class CreditCardPayment implements PaymentStrategy {
  pay(): void {
    console.log("Credit card payment processed");
  }
}

class PayPalPayment implements PaymentStrategy {
  pay(): void {
    console.log("PayPal payment processed");
  }
}

class UPIPayment implements PaymentStrategy {
  pay(): void {
    console.log("UPI payment processed");
  }
}


class PaymentProcessor {
  constructor(private strategy: PaymentStrategy) {}

  process(): void {
    this.strategy.pay();
  }
}
```

Usage:

```typescript
const processor = new PaymentProcessor(new UPIPayment());
processor.process();

// Add CryptoPayment in future — no change to PaymentProcessor code
```

**Example 1:** Let’s say we want to apply offers on movie tickets.

```typescript
class DiscountEngine {
  calculateDiscount(type: string, amount: number): number {
    if (type === "student") {
      return amount * 0.1;
    } else if (type === "seasonal") {
      return amount * 0.2;
    }
    return 0;
  }
}
```

Every time a new discount is added, the class must be changed → violates OCP

Refactored code:

```typescript
interface DiscountStrategy {
  getDiscount(amount: number): number;
}

class StudentDiscount implements DiscountStrategy {
  getDiscount(amount: number): number {
    return amount * 0.1;
  }
}

class SeasonalDiscount implements DiscountStrategy {
  getDiscount(amount: number): number {
    return amount * 0.2;
  }
}

class NoDiscount implements DiscountStrategy {
  getDiscount(amount: number): number {
    return 0;
  }
}

class DiscountEngine {
  constructor(private strategy: DiscountStrategy) {}

  applyDiscount(amount: number): number {
    return amount - this.strategy.getDiscount(amount);
  }
}
```

Usage:

```typescript

console.log(engine.applyDiscount(500)); // 450
```

# Liskov Substitution Principle (LSP)

**Definition:** *If S is a subtype of T, then objects of type T should be replaceable with objects of type S without breaking the program.*

In simple English: You should be able to use a child class anywhere the parent class is expected, and it should work the same, without surprises, bugs, or broken behaviour.

## What is the Idea behind it?

- Child classes should respect the behaviour expected from their parent.
- Inheritance should be behaviorally correct, not just syntactically valid.
- If a derived class violates the expectations of the base class, it breaks LSP

Even if you didn’t understand the theory, just keep the theory in mind. Examples will make everything crystal clear.

We will take the classic example of a Square and a Rectangle, then we will go for a real-world example.

```typescript
class Rectangle {
  constructor(public width: number, public height: number) {}

  setWidth(w: number): void {
    this.width = w;
  }

  setHeight(h: number): void {
    this.height = h;
  }

  getArea(): number {
    return this.width * this.height;
  }
}

class Square extends Rectangle {
  setWidth(w: number): void {
    this.width = w;
    this.height = w;
  }

  setHeight(h: number): void {
    this.width = h;
    this.height = h;
  }
}
```

In the above code, Rectangle is parent class and Square is its child class.

```
function printArea(rect: Rectangle) {
  rect.setWidth(5);
  rect.setHeight(10);
  console.log(rect.getArea()); // Expected 50
}

const rect = new Rectangle(2, 3);
printArea(rect); // OK → 50

const square = new Square(2, 2);
printArea(square); // Wrong: 100 (because both width and height became 10)
```

In the printArea() function, when we are replacing the parent class with its child class, the behaviour breaks, so it is violating LSP.

Refactor the code:

```typescript
interface Shape {
  getArea(): number;
}

class Rectangle implements Shape {
  constructor(public width: number, public height: number) {}

  getArea(): number {
    return this.width * this.height;
  }
}

class Square implements Shape {
  constructor(public side: number) {}

  getArea(): number {
    return this.side * this.side;
  }
}
function printArea(shape: Shape) {
  console.log(shape.getArea());
}

printArea(new Rectangle(5, 10)); // 50
printArea(new Square(10));       // 100
```

Now Shape is a parent, and when we replace Shape with any of its children (Rectangle, Square), it does not break the functionality.

Let's take another example to understand it.

**Example 1:**

```typescript
interface NotificationService {
  send(userId: string, message: string): void;
}

```

Maybe the above example will seem very intuitive, but what I want to say is that always try to replace the parent class with all child classes. If everything is working fine, then your code is obeying LSP.

This principle is very easy to understand, so I don’t think more examples are required. We are moving forward to the next principle.

# Interface Segregation Principle (ISP)

Definition: *Clients should not be forced to depend on interfaces they do not use.*

In simple English: Don’t make classes implement methods they don’t need.
Break large interfaces into smaller, focused ones.

Let’s say we define a RemoteControl interface:

```typescript
interface RemoteControl {
  turnOn(): void;
  turnOff(): void;
  record(): void;
}
```

Suppose, above interface is implemented by TV and Camera
**TV**: supports `turnOn/Off`**Camera**: supports `turnOn/Off,record`

But forcing TV to implement `record()` voilates ISP.

We will be taking some more examples to understand it.

**Example 1:**

```typescript
interface PaymentGateway {
  pay(): void;
  refund(): void;
  schedule(): void;
}
```

Now imagine:

- `StripePayment` → supports all methods
- `CashOnDelivery` → supports only `pay()` but forced to implement `refund()` and `schedule()` which it can’t support

```typescript
class CashOnDelivery implements PaymentGateway {
  pay(): void {
    console.log("COD payment");
  }

  refund(): void {
    throw new Error("Refund not supported for COD");
  }

  schedule(): void {
    throw new Error("Scheduling not supported");
  }
}
```

To fix it, break the interface into multiple interfaces.

```typescript
interface Payable {
  pay(): void;
}

interface Refundable {
  refund(): void;
}

interface Schedulable {
  schedule(): void;
}
class CashOnDelivery implements Payable {
  pay(): void {
    console.log("COD payment");
  }
}

class StripePayment implements Payable, Refundable, Schedulable {
  // implements all
}
```

**Example 2:**

```typescript
interface ReportGenerator {
  generatePDF(): void;
  generateExcel(): void;
  generateCSV(): void;
}
```

Now you have:

- `BillingReport` → supports PDF and Excel
- `UserActivityReport` → supports only CSV

```typescript
class UserActivityReport implements ReportGenerator {
  generatePDF(): void {
    throw new Error("Not supported");
  }

  generateExcel(): void {
    throw new Error("Not supported");
  }

  generateCSV(): void {
    console.log("Generating CSV");
  }
}
```

This breaks ISP — UserActivityReport is forced to implement unused methods.

Fix: Break it into multiple interfaces.

```typescript
interface PDFGeneratable {
  generatePDF(): void;
}

interface ExcelGeneratable {
  generateExcel(): void;
}

interface CSVGeneratable {
  generateCSV(): void;
}
class UserActivityReport implements CSVGeneratable {
  generateCSV(): void {
    console.log("Generating user CSV");
  }
}

class BillingReport implements PDFGeneratable, ExcelGeneratable, CSVGeneratable {
  generatePDF(): void {
    console.log("Generating user PDF");
  }
  generateExcel(): void {
    console.log("Generating user Excel");
  }
  generateCSV(): void {
    console.log("Generating user CSV");
  }
}
```

**Example 2:**

```typescript
interface FileHandler {
  open(): void;
  read(): string;
  write(data: string): void;
  close(): void;
}
```

Now imagine:

- `LogFileReader`: only needs `open`, `read`, `close`
- `LogFileWriter`: only needs `open`, `write`, `close`

```typescript
class LogFileReader implements FileHandler {
  open(): void { /* ok */ }
  read(): string { return "log"; }
  write(data: string): void {
    throw new Error("Reader can't write");
  }
  close(): void { /* ok */ }
}
```

The above code violates ISP because LogFileWriter has to forcefully implement write().

Fix:

```typescript
interface FileOpener {
  open(): void;
  close(): void;
}

interface FileReader extends FileOpener {
  read(): string;
}

interface FileWriter extends FileOpener {
  write(data: string): void;
}
class LogFileReader implements FileReader {
  open() {}
  read() { return "log"; }
  close() {}
}
```

I guess this should be enough to completely understand ISP.

Just remember these:

- Split large interfaces into small, role-based contracts
- Don’t force classes to depend on things they don’t use
- Avoid `throw new Error("Not implemented")`

# Dependency Inversion Principle (DIP)

**Definition:** *High-level modules should not depend on low-level modules. Both should depend on abstractions.
Abstractions should not depend on details. Details should depend on abstractions.*

In simple English: Your **business logic (high-level)** shouldn’t directly depend on **concrete classes (low-level)**. Instead, **both** should depend on **interfaces (abstractions)**.

Suppose your code flows like this:

API -> Controller Layer -> Service Layer -> Repository Layer

- In the Controller Layer, you accept the request from the API.
- In the Service Layer, you pass the API arguments and do computation and all business logic.
- In Repository Layer, you interact with databases or external service to persist or get data.

Suppose we are building a Ticketing booking system. Now, we will write code without following DIP.

```typescript
// TicketRepository.ts
export class TicketRepository {
  async bookTicket(userId: string, movieId: string): Promise<string> {
    console.log(`Saving booking in DB for user ${userId} and movie ${movieId}`);
    return "booking-id-123";
  }
}
// BookTicketService.ts
import { TicketRepository } from './TicketRepository';

export class BookTicketService {
  private repo = new TicketRepository(); // tightly coupled

  async execute(userId: string, movieId: string): Promise<string> {
    // do business logic here also
    return this.repo.bookTicket(userId, movieId);
  }
}
// BookTicketController.ts
import { BookTicketService } from './BookTicketService';

export class BookTicketController {
  private service = new BookTicketService(); // tightly coupled

  async handleRequest(req: any): Promise<any> {
    const { userId, movieId } = req.body;
    const bookingId = await this.service.execute(userId, movieId);
    return { success: true, bookingId };
  }
}
```

Running everything:

```typescript
// index.ts
import { BookTicketController } from './BookTicketController';

const controller = new BookTicketController();

(async () => {
  const req = { body: { userId: "u1", movieId: "m101" } };
  const response = await controller.handleRequest(req);
  console.log(response); // { success: true, bookingId: 'booking-id-123' }
})();
```

The above code doesn’t follow DIP because a higher-level module like BookTicketService depends on the concrete implementation of TicketRepository instead of the interface.

It has several disadvantages

- Cannot switch from MySQL to Mongo. Repo is hard-coded.
- Tight coupling everywhere. Every change cascades across layers
- Breaks Open/Closed Principle. You have to classes instead of extending.
- Violates Single Responsibility Principle. Classes are responsible for wiring dependencies, too.

Good practice is that a higher-level module should depend on the interface instead of concrete classes.

Fix code:

```typescript
// ITicketRepository.ts
export interface ITicketRepository {
  bookTicket(userId: string, movieId: string): Promise<string>;
}

// TicketRepository.ts
import { ITicketRepository } from './ITicketRepository';

export class TicketRepository implements ITicketRepository {
  async bookTicket(userId: string, movieId: string): Promise<string> {
    // simulate DB save
    console.log(`Saving booking in DB for user ${userId} and movie ${movieId}`);
    return "booking-id-123";
  }
}
```

**High-level** module depends on **interface**, not on `TicketRepository` directly — DIP applied

```typescript
// BookTicketService.ts
import { ITicketRepository } from './ITicketRepository';

export class BookTicketService {
  constructor(private repo: ITicketRepository) {}

  async execute(userId: string, movieId: string): Promise<string> {
    // business logic can go here (validation, rules)
    return this.repo.bookTicket(userId, movieId);
  }
}
// BookTicketController.ts
import { BookTicketService } from './BookTicketService';

export class BookTicketController {
  constructor(private service: BookTicketService) {}

  async handleRequest(req: any): Promise<any> {
    const { userId, movieId } = req.body;
    const bookingId = await this.service.execute(userId, movieId);
    return { success: true, bookingId };
  }
}
```

Wire it all up

```typescript
// index.ts
import { TicketRepository } from './TicketRepository';
import { BookTicketService } from './BookTicketService';
import { BookTicketController } from './BookTicketController';

const repo = new TicketRepository();
const service = new BookTicketService(repo);
const controller = new BookTicketController(service);

// Simulate request
(async () => {
  const fakeRequest = { body: { userId: "u1", movieId: "m101" } };
  const response = await controller.handleRequest(fakeRequest);
  console.log(response); // { success: true, bookingId: 'booking-id-123' }
})();
```

You may be observing that BookTicketService depends on the interface of the Repository instead of a concrete class. But BookTicketController directly depend upon the class BookTicketService instead of the interface.
Well, making the interface of the Service layer may or may not be worth it.
Because the implementation of the Repo layer may change, like changing MySQL to MongoDB, but if you are changing the service layer, then you should write a new API altogether instead of changing the implementation of the service layer.
