# 介绍

无论你是在构建一个小脚本还是设计大型应用程序，你今天如何组织代码将决定明天适应变化有多容易。这就是 **SOLID原则** 的用武之地。

这些原则是由 **罗伯特·C·马丁 (鲍勃大叔)** 提出的。如果你在编写应用程序时遵循这些原则，当代码变得非常庞大时，它不会变得一团糟，而且你可以很容易地添加新功能。

说到SOLID原则，开发人员之间存在很多误解和混淆，但我可以保证，读完这篇博客后，你不会有任何困惑，并且可以在实际编码中应用它。

我们将使用 **Typescript** 来编写代码片段。概念更重要；代码可以用任何语言编写，但如果你不想读typescript，你可以用ChatGPT将代码片段转换为你喜欢的编程语言。

SOLID原则的全称：

- **S:** 单一职责原则 (Single Responsibility Principle)
- **O:** 开放/封闭原则 (Open/Closed Principle)
- **L:** 里氏替换原则 (Liskov Substitution Principle)
- **I:** 接口隔离原则 (Interface Segregation Principle)
- **D:** 依赖倒置原则 (Dependency Inversion Principle)

# 单一职责原则 (SRP)

定义：*一个类应该只有一个改变的理由。*

意味着一个类应该只有那些因单一原因而改变或只受一个来源影响的方法。简单来说，如果将来你想修改一个类的代码，那么你每次都应该只因为一个单一来源而修改该类代码。

光看定义可能不太明白，让我们通过多个例子来弄清楚。

```typescript
class TicketBooking {
  constructor(
    private movieId: number,
    private userId: number,
    private seatNumber: string
  ) {}

  checkSeatAvailability(): boolean {
    // 检查座位是否可用的逻辑
    return true;
  }

  calculatePrice(): number {
    // 基于座位类型、时间的价格逻辑
    return 300;
  }

  makePayment(): boolean {
    // 调用支付网关API
    return true;
  }

  sendConfirmation(): void {
    // 发送短信或电子邮件
  }

  book(): void {
    if (this.checkSeatAvailability()) {
      const price = this.calculatePrice();
      const paid = this.makePayment();
      if (paid) {
        this.sendConfirmation();
        console.log('预订成功！');
      }
    }
  }
}
```

上面的代码违反了SRP，因为它有4个逻辑上的改变理由：

- 座位检查逻辑改变
- 价格政策改变
- 支付网关改变
- 通知/确认逻辑改变

支付和价格由不同的团队处理，所以如果明天支付方式改变或价格政策改变，你需要修改TicketBooking类。有4个来源可以改变这个类的代码，所以这违反了SRP。一个类应该只因为一个来源而改变。

要纠正上面的代码，我们需要将其拆分为多个类，每个类只能因单一来源或原因而改变。

```typescript
class SeatChecker {
  isSeatAvailable(movieId: number, seatNumber: string): boolean {
    // 检查数据库中座位是否空闲
    return true;
  }
}
class PriceCalculator {
  getPrice(movieId: number, seatNumber: string): number {
    // 基于座位类型、时间等的逻辑
    return 300;
  }
}
class PaymentService {
  pay(userId: number, amount: number): boolean {
    // 支付网关集成
    console.log(`正在为用户 ${userId} 处理 ₹${amount} 的付款`);
    return true;
  }
}
class Notifier {
  sendConfirmation(userId: number, movieId: number): void {
    // 发送电子邮件/短信
    console.log(`已向用户 ${userId} 发送电影 ${movieId} 的确认信息`);
  }
}
```

现在，TicketingBooking类协调一切

```typescript
class TicketBooking {
  constructor(
    private seatChecker: SeatChecker,
    private priceCalculator: PriceCalculator,
    private paymentService: PaymentService,
    private notifier: Notifier
  ) {}

  bookTicket(userId: number, movieId: number, seatNumber: string) {
    if (this.seatChecker.isSeatAvailable(movieId, seatNumber)) {
      const price = this.priceCalculator.getPrice(movieId, seatNumber);
      const paid = this.paymentService.pay(userId, price);
      if (paid) {
        this.notifier.sendConfirmation(userId, movieId);
        console.log("预订成功！");
      } else {
        console.log("支付失败！");
      }
    } else {
      console.log("座位不可用！");
    }
  }
}
```

大多数人混淆SRP，认为一个类应该只包含一个方法，但这是错误的。它可以有多个方法。有些人认为SRP就像一个类只处理一件事。但那样想很容易混淆。

所以只需记住，SRP意味着一个类应该只包含那些将来会因单一来源或原因而改变的方法集。

我们将举更多例子来理解

**例1：**

```typescript
class Order {
  private items: string[] = [];

  addItem(item: string) {
    this.items.push(item);
  }

  removeItem(item: string) {
    this.items = this.items.filter(i => i !== item);
  }

  getTotalPrice(): number {
    return this.items.length * 100;
  }
}
```

上面的代码是否违反SRP？
答：不，因为所有方法都与一件事相关：管理 **订单** 的内容。一个改变的理由：如果关于订单的业务规则（如定价、项目处理）改变。

**例2：**

```typescript
class UserProfileManager {
  getProfile(userId: number): UserProfile {
    // 从数据库获取用户
  }

  updateProfile(userId: number, data: Partial<UserProfile>): void {
    // 保存新的用户资料
  }

  uploadProfilePicture(userId: number, image: File): void {
    // 保存图片到S3
  }

  deleteAccount(userId: number): void {
    // 从数据库删除用户并清除会话
  }

```

所有方法似乎都与"用户相关"——所以开发人员认为这是单一职责。但它没有遵循SRP。

- getProfile、updateProfile类似。它们只在用户数据更改时更改。
- uploadProfilePicture在基础设施更改时更改。假设你在AWS S3中存储图像，如果明天你开始在Cloudflare R2中存储图像，那么uploadProfilePicture会更改。
- deleteAccount：它可能由于许多原因而发生，如违反政策、不活动等。意味着当你的业务政策更改时，此方法会更改。

由于上面的类有3个更改的理由，因此必须将其拆分为3个单独的类，每个类只有一个更改的理由。

```typescript
class UserProfileService {
  get(userId: number): UserProfile { /* ... */ }
  update(userId: number, data: Partial<UserProfile>) { /* ... */ }
}

class UserPictureService {
  upload(userId: number, file: File) { /* 上传到S3 */ }
}

  delete(userId: number) { /* 从数据库、会话中删除 */ }
}
```

# 开放/封闭原则 (OCP)

定义：*软件实体（类、模块、函数）应该对扩展开放，对修改封闭。*

## 这实际上意味着什么？

- **对扩展开放** → 你可以添加新功能
- **对修改封闭** → 你不应该更改现有的经过测试的代码来实现它

**目标：** 添加新功能而不破坏现有逻辑

看下面的代码：

```typescript
class PaymentProcessor {
  process(paymentMethod: string): void {
    if (paymentMethod === "credit_card") {
      console.log("处理信用卡支付...");
    } else if (paymentMethod === "paypal") {
      console.log("处理PayPal支付...");
    } else if (paymentMethod === "upi") {
      console.log("处理UPI支付...");
    } else {
      throw new Error("不支持的支付方式");
    }
  }
}
```

上面的代码违反了OCP，因为：每次添加新方法（如Stripe、加密货币支付）时，你必须：

- 修改此类
- 有破坏现有代码的风险
- 添加更多的`if-else`

这既不具有可扩展性也不具有可维护性。

要修复它，我们必须使代码无需更改PaymentProcessor类的代码（对修改封闭），并且仍然可以在将来添加新的支付方式（对扩展开放）。

我们不应该在PaymentProcessor类中编写每种支付方式的实现，而应该接受一个"接口"并调用该接口的方法。在调用类时，我们应该根据我们需要的任何支付方式提供具体实现。下面是重构后的代码：

```typescript
interface PaymentStrategy {
  pay(): void;
}

class CreditCardPayment implements PaymentStrategy {
  pay(): void {
    console.log("信用卡支付已处理");
  }
}

class PayPalPayment implements PaymentStrategy {
  pay(): void {
    console.log("PayPal支付已处理");
  }
}

class UPIPayment implements PaymentStrategy {
  pay(): void {
    console.log("UPI支付已处理");
  }
}


class PaymentProcessor {
  constructor(private strategy: PaymentStrategy) {}

  process(): void {
    this.strategy.pay();
  }
}
```

用法：

```typescript
const processor = new PaymentProcessor(new UPIPayment());
processor.process();

// 将来添加CryptoPayment — 无需更改PaymentProcessor代码
```

我们将做更多的例子来使其更加清晰：

**例1：** 假设我们想对电影票应用优惠。

```typescript
class DiscountEngine {
  calculateDiscount(type: string, amount: number): number {
    if (type === "student") {
      return amount * 0.1;
    } else if (type === "seasonal") {
      return amount * 0.2;
    }
    return 0;
  }
}
```

每次添加新折扣时，必须更改类 → 违反OCP

重构代码：

```typescript
interface DiscountStrategy {
  getDiscount(amount: number): number;
}

class StudentDiscount implements DiscountStrategy {
  getDiscount(amount: number): number {
    return amount * 0.1;
  }
}

class SeasonalDiscount implements DiscountStrategy {
  getDiscount(amount: number): number {
    return amount * 0.2;
  }
}

class NoDiscount implements DiscountStrategy {
  getDiscount(amount: number): number {
    return 0;
  }
}

class DiscountEngine {
  constructor(private strategy: DiscountStrategy) {}

  applyDiscount(amount: number): number {
    return amount - this.strategy.getDiscount(amount);
  }
}
```

```typescript
const engine = new DiscountEngine(new StudentDiscount());
console.log(engine.applyDiscount(500)); // 450
```


# 里氏替换原则 (LSP)

**定义：** *如果S是T的子类型，那么类型T的对象应该可以被类型S的对象替换，而不会破坏程序。*

简单来说：你应该能够在任何期望父类的地方使用子类，并且它应该同样工作，没有意外、错误或破坏行为。

## 其背后的思想是什么？

- 子类应该尊重从父类期望的行为。
- 继承应该在行为上是正确的，而不仅仅是语法上有效。
- 如果派生类违反了基类的期望，它就违反了LSP

即使你不理解理论，只需记住理论。例子会让一切变得清晰。

我们将采用正方形和长方形的经典例子，然后我们将看一个现实世界的例子。

```typescript
class Rectangle {
  constructor(public width: number, public height: number) {}

  setWidth(w: number): void {
    this.width = w;
  }

  setHeight(h: number): void {
    this.height = h;
  }

  getArea(): number {
    return this.width * this.height;
  }
}

class Square extends Rectangle {
  setWidth(w: number): void {
    this.width = w;
    this.height = w;
  }

  setHeight(h: number): void {
    this.width = h;
    this.height = h;
  }
}
```

在上面的代码中，Rectangle是父类，Square是其子类。

```typescript
function printArea(rect: Rectangle) {
  rect.setWidth(5);
  rect.setHeight(10);
  console.log(rect.getArea()); // 期望50
}

const rect = new Rectangle(2, 3);
printArea(rect); // 正常 → 50

const square = new Square(2, 2);
printArea(square); // 错误：100（因为宽度和高度都变成了10）
```

在printArea()函数中，当我们用其子类替换父类时，行为被破坏，所以它违反了LSP。

重构代码：

```typescript
interface Shape {
  getArea(): number;
}

class Rectangle implements Shape {
  constructor(public width: number, public height: number) {}

  getArea(): number {
    return this.width * this.height;
  }
}

class Square implements Shape {
  constructor(public side: number) {}

  getArea(): number {
    return this.side * this.side;
  }
}
function printArea(shape: Shape) {
  console.log(shape.getArea());
}

printArea(new Rectangle(5, 10)); // 50
printArea(new Square(10));       // 100
```

现在Shape是父类，当我们用它的任何子类（Rectangle、Square）替换Shape时，它不会破坏功能。

让我们再举一个例子来理解它。

**例1：**

```typescript
interface NotificationService {
  send(userId: string, message: string): void;
}

class EmailService implements NotificationService {
  send(userId: string, message: string): void {
    console.log("电子邮件已发送");
  }
}

class DummyNotification implements NotificationService {
  send(userId: string, message: string): void {
    throw new Error("在测试环境中禁用");
  }
}
function notify(service: NotificationService) {
  service.send("u123", "您的票已预订");
}

notify(new EmailService());
notify(new DummyNotification());  // 运行时崩溃
```

用子类（DummyNotification）替换NotificationService会抛出错误。

修复：

```typescript
class DummyNotification implements NotificationService {
  send(userId: string, message: string): void {
    console.log("[测试环境] 通知已跳过");
  }
}
```

上面的例子可能看起来很直观，但我想说的是，总是尝试用所有子类替换父类。如果一切正常工作，那么你的代码就遵循了LSP。

这个原则很容易理解，所以我认为不需要更多的例子。我们继续下一个原则。

# 接口隔离原则 (ISP)

定义：*客户端不应该被迫依赖于它们不使用的接口。*

简单来说：不要让类实现它们不需要的方法。将大接口拆分为更小、更集中的接口。

假设我们定义一个RemoteControl接口：

```typescript
interface RemoteControl {
  turnOn(): void;
  turnOff(): void;
  record(): void;
}
```

假设，上面的接口由TV和Camera实现
**TV**：支持`turnOn/Off`
**Camera**：支持`turnOn/Off,record`

但强迫TV实现`record()`违反了ISP。

我们将举更多例子来理解它。

**例1：**

```typescript
interface PaymentGateway {
  pay(): void;
  refund(): void;
  schedule(): void;
}
```

现在想象：

- `StripePayment` → 支持所有方法
- `CashOnDelivery` → 只支持`pay()`，但被迫实现它不支持的`refund()`和`schedule()`

```typescript
class CashOnDelivery implements PaymentGateway {
  pay(): void {
    console.log("货到付款");
  }

  refund(): void {
    throw new Error("货到付款不支持退款");
  }

  schedule(): void {
    throw new Error("不支持调度");
  }
}
```

要修复它，将接口拆分为多个接口。

```typescript
interface Payable {
  pay(): void;
}

interface Refundable {
  refund(): void;
}

interface Schedulable {
  schedule(): void;
}
class CashOnDelivery implements Payable {
  pay(): void {
    console.log("货到付款");
  }
}

class StripePayment implements Payable, Refundable, Schedulable {
  // 实现所有方法
}
```

**例2：**

```typescript
interface ReportGenerator {
  generatePDF(): void;
  generateExcel(): void;
  generateCSV(): void;
}
```

现在你有：

- `BillingReport` → 支持PDF和Excel
- `UserActivityReport` → 只支持CSV

```typescript
class UserActivityReport implements ReportGenerator {
  generatePDF(): void {
    throw new Error("不支持");
  }

  generateExcel(): void {
    throw new Error("不支持");
  }

  generateCSV(): void {
    console.log("生成CSV");
  }
}
```

这违反了ISP — UserActivityReport被迫实现未使用的方法。

修复：将其拆分为多个接口。

```typescript
interface PDFGeneratable {
  generatePDF(): void;
}

interface ExcelGeneratable {
  generateExcel(): void;
}

interface CSVGeneratable {
  generateCSV(): void;
}
class UserActivityReport implements CSVGeneratable {
  generateCSV(): void {
    console.log("生成用户CSV");
  }
}

class BillingReport implements PDFGeneratable, ExcelGeneratable, CSVGeneratable {
  generatePDF(): void {
    console.log("生成用户PDF");
  }
  generateExcel(): void {
    console.log("生成用户Excel");
  }
  generateCSV(): void {
    console.log("生成用户CSV");
  }
}
```

**例2：**

```typescript
interface FileHandler {
  open(): void;
  read(): string;
  write(data: string): void;
  close(): void;
}
```

现在想象：

- `LogFileReader`：只需要`open`、`read`、`close`
- `LogFileWriter`：只需要`open`、`write`、`close`

```typescript
class LogFileReader implements FileHandler {
  open(): void { /* 可以 */ }
  read(): string { return "log"; }
  write(data: string): void {
    throw new Error("读取器不能写入");
  }
  close(): void { /* 可以 */ }
}
```

上面的代码违反了ISP，因为LogFileWriter不得不强制实现write()。

修复：

```typescript
interface FileOpener {
  open(): void;
  close(): void;
}

interface FileReader extends FileOpener {
  read(): string;
}

interface FileWriter extends FileOpener {
  write(data: string): void;
}
class LogFileReader implements FileReader {
  open() {}
  read() { return "log"; }
  close() {}
}
```

我想这应该足以完全理解ISP了。

只需记住这些：

- 将大接口拆分为小的、基于角色的契约
- 不要强迫类依赖于它们不使用的东西
- 避免`throw new Error("未实现")`

# 依赖倒置原则 (DIP)

**定义：** *高层模块不应该依赖低层模块。两者都应该依赖抽象。抽象不应该依赖细节。细节应该依赖抽象。*

简单来说：你的 **业务逻辑（高层）** 不应该直接依赖于 **具体类（低层）**。相反，**两者** 都应该依赖于 **接口（抽象）**。

假设你的代码流程如下：

API -> 控制器层 -> 服务层 -> 存储库层

- 在控制器层，你接受来自API的请求。
- 在服务层，你传递API参数并进行计算和所有业务逻辑。
- 在存储库层，你与数据库或外部服务交互以持久化或获取数据。

假设我们正在构建一个票务预订系统。现在，我们将编写不遵循DIP的代码。

```typescript
// TicketRepository.ts
export class TicketRepository {
  async bookTicket(userId: string, movieId: string): Promise<string> {
    console.log(`为用户 ${userId} 和电影 ${movieId} 保存预订到数据库`);
    return "booking-id-123";
  }
}
// BookTicketService.ts
import { TicketRepository } from './TicketRepository';

export class BookTicketService {
  private repo = new TicketRepository(); // 紧密耦合

  async execute(userId: string, movieId: string): Promise<string> {
    // 也在这里做业务逻辑
    return this.repo.bookTicket(userId, movieId);
  }
}
// BookTicketController.ts
import { BookTicketService } from './BookTicketService';

export class BookTicketController {
  private service = new BookTicketService(); // 紧密耦合

  async handleRequest(req: any): Promise<any> {
    const { userId, movieId } = req.body;
    const bookingId = await this.service.execute(userId, movieId);
    return { success: true, bookingId };
  }
}
```

运行一切：

```typescript
// index.ts
import { BookTicketController } from './BookTicketController';

const controller = new BookTicketController();

(async () => {
  const req = { body: { userId: "u1", movieId: "m101" } };
  const response = await controller.handleRequest(req);
  console.log(response); // { success: true, bookingId: 'booking-id-123' }
})();
```

上面的代码不遵循DIP，因为像BookTicketService这样的高层模块依赖于TicketRepository的具体实现，而不是接口。

它有几个缺点

- 不能从MySQL切换到Mongo。存储库是硬编码的。
- 到处都是紧密耦合。每个更改都会级联到各个层
- 违反开放/封闭原则。你必须修改类而不是扩展。
- 违反单一职责原则。类还负责连接依赖项。

良好的做法是高层模块应该依赖于接口而不是具体类。

修复代码：

```typescript
// ITicketRepository.ts
export interface ITicketRepository {
  bookTicket(userId: string, movieId: string): Promise<string>;
}

// TicketRepository.ts
import { ITicketRepository } from './ITicketRepository';

export class TicketRepository implements ITicketRepository {
  async bookTicket(userId: string, movieId: string): Promise<string> {
    // 模拟数据库保存
    console.log(`为用户 ${userId} 和电影 ${movieId} 保存预订到数据库`);
    return "booking-id-123";
  }
}
```

**高层** 模块依赖于 **接口**，而不是直接依赖于`TicketRepository` — 应用了DIP

```typescript
// BookTicketService.ts
import { ITicketRepository } from './ITicketRepository';

export class BookTicketService {
  constructor(private repo: ITicketRepository) {}

  async execute(userId: string, movieId: string): Promise<string> {
    // 业务逻辑可以在这里（验证、规则）
    return this.repo.bookTicket(userId, movieId);
  }
}
// BookTicketController.ts
import { BookTicketService } from './BookTicketService';

export class BookTicketController {
  constructor(private service: BookTicketService) {}

  async handleRequest(req: any): Promise<any> {
    const { userId, movieId } = req.body;
    const bookingId = await this.service.execute(userId, movieId);
    return { success: true, bookingId };
  }
}
```

连接所有组件

```typescript
// index.ts
import { TicketRepository } from './TicketRepository';
import { BookTicketService } from './BookTicketService';
import { BookTicketController } from './BookTicketController';

const repo = new TicketRepository();
const service = new BookTicketService(repo);
const controller = new BookTicketController(service);

// 模拟请求
(async () => {
  const fakeRequest = { body: { userId: "u1", movieId: "m101" } };
  const response = await controller.handleRequest(fakeRequest);
  console.log(response); // { success: true, bookingId: 'booking-id-123' }
})();
```

你可能注意到BookTicketService依赖于存储库的接口，而不是具体类。但BookTicketController直接依赖于BookTicketService类而不是接口。
嗯，为服务层创建接口可能值得也可能不值得。
因为存储库层的实现可能会改变，比如从MySQL更改为MongoDB，但如果你要更改服务层，那么你应该编写一个新的API，而不是更改服务层的实现。
