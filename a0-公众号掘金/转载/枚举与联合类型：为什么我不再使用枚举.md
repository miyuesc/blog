# 枚举与联合类型：为什么我不再使用枚举

> 原文：[《Enums vs Union Types: Why I Stopped Using Enums Everywhere》](https://medium.com/@ie33/enums-vs-union-types-why-i-stopped-using-enums-everywhere-30b3c5ea5af8)
>
> 作者：[IE 33](https://medium.com/@ie33)



> I used Enums by default in TypeScript, they seemed like the perfect way to define a set of named values.



That was until a colleague during a code review wrote me this comment :

> "Why don't you just use a Union Type? It's better and more performant."

That one question made me stop and think: **Had I been using Enums wrong all along ?**

I decided to dig deeper, compare both approaches, and share it with you.

### The Problem with Enums :

let's take a look to this example :

```typescript
Copyenum BoxType {
  PRIMARY = "primary",
  INFO = "info",
  ERROR = "error"
}

const alertBoxType: BoxType = BoxType.PRIMARY;
console.log(alertBoxType); // "primary"
```

As you can see, Enum **looks clean and structured**.

let's now take a look to javascript code generated : (I used this [online tool](https://transform.tools/typescript-to-javascript))

```javascript
Copyvar BoxType;

(function(BoxType) {
  BoxType["PRIMARY"] = "primary"
  BoxType["INFO"] = "info"
  BoxType["ERROR"] = "error"
})(BoxType || (BoxType = {}))

const alertBoxType = BoxType.PRIMARY
console.log(alertBoxType) // "primary"
```

When TypeScript compiles this Enum, it turns into a JavaScript **object !**

Wait…What ?! I thought Enums were just types, but they actually create extra runtime objects.

So, **Problems with this approach:** - **Extra JavaScript code =>** larger bundle size. - **Slower performance** **=>** needs object lookup.

### The Better Alternative → Union Types :

Union Types, on the other hand, **don't exist at runtime**. They are purely **TypeScript constructs**, which means they **disappear after compilation**.

let's do the same previous example but using union types :

```typescript
Copytype BoxType = "primary" | "info" | "error";

const alertBoxType: BoxType = "primary";
console.log(alertBoxType); // "primary"
```

When TypeScript compiles this, the output is clean, look:

```javascript
Copy"use strict";
const alertBoxType = "primary"
console.log(alertBoxType) // "primary"
```

**What changed?** + **Union Types are fully disappeared at compile time =>** small bundle size. + **Direct string comparison =>** better performance.

But sometimes using Enums is necessary.

### When using Enums is necessary ?

- One major advantage of Enums is **reverse lookup** — meaning you can retrieve the key from the value.

let's give an example :

```typescript
Copyenum HttpStatus {
  OK = 200,
  NOT_FOUND = 404,
  INTERNAL_SERVER = 500,
}

console.log(HttpStatus.OK); // 200
console.log(HttpStatus[200]); // "OK"
```

`HttpStatus[200]` returns `"OK"`—this is not possible with Union Types.

- Another advantage of Enums : **using numeric enums to keep mapping clear,** let's take an example to clarify it :

```typescript
Copyenum UserRole {
  Admin = 1,
  Editor = 2,
  Viewer = 3,
}

const getUserRole = (roleId: number): string => {
  return UserRole[roleId] || "Unknown";
};

console.log(getUserRole(1)); // "Admin"
console.log(getUserRole(4)); // "Unknown" (not in Enum)
```

As you see in the example above Enums make it easy to **map IDs to readable names**.

### To sum up :

I follow this simple rule :

\- Use **Union Types** for most cases. - Use **Enums** only when they provide a real advantage. (like reverse lookup or mapping numeric values)

Next time someone asks *"Why don't you use a Union Type instead?"*, you'll know exactly why =D
