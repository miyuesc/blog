# WebAssembly 何时会获得 DOM 支持？

> [When Is WebAssembly Going to Get DOM Support?](https://queue.acm.org/detail.cfm?id=3746174)
> 
> [Daniel Ehrenberg]()

WebAssembly（Wasm）真的准备好在 Web 应用中投入生产使用了吗？尽管这种使用需要与网页以及操纵网页的 API（如 DOM）进行集成。

这个问题的答案可以同时是："Wasm 可能永远不会获得*直接* DOM 访问权"，以及"是的，Wasm 已经准备好各种 Web 集成用途，从第一天起就支持（通过一点间接方式）调用 DOM"。

让我来解释一下。

WebAssembly 从设计之初就与 JavaScript 严格分离。与 [asm.js](https://developer.mozilla.org/en-US/docs/Games/Tools/asm.js)（developer.mozilla.org）不同，asm.js 不可避免地嵌入在 JavaScript 中，而核心的 Wasm 字节码格式完全摆脱了 JavaScript 的所有"遗留问题"。同时，正如其名称所示，Wasm 是 Web 平台的一部分。

那么，为什么像 DOM 这样的 Web API 仍然与 JavaScript 绑定，为什么没有新的 Wasm 版本呢？

答案是，不需要为 Web API（如 DOM）开发新版本就能让它们在 Wasm 中使用；现有的 JavaScript API 工作得很好。

当在浏览器或其他 JavaScript 环境中使用时，Wasm 包含各种 JavaScript API，允许编译器生成的胶水代码无缝访问任何 JavaScript 代码。

WebAssembly 一直在逐步发展，允许构建工具链生成更少的代码，特别是更少的 JavaScript。这些改进针对的是那些使实际 Web 应用在 Wasm 中运行缓慢且体积庞大的代码。
Wasm 与 JavaScript 的集成将通过 W3C Wasm CG（社区组）的工作继续发展和深化。

也许，如果事实证明某种机制能带来性能和代码大小的改进，足以证明其复杂性是合理的，那么未来可能会添加一种直接从 Wasm 调用 Web API 的机制，但这种机制的设计和实现需要巨大的努力。

另一方面，一点用于连接 Web API 的 JavaScript 胶水可能不是需要担心的瓶颈，尤其是当还有其他开销来源需要解决时。

 

### 将 Wasm 与 JavaScript 结合起来

为了理解 Wasm 和 JavaScript 如何结合，让我们看一个改编自 [MDN 上 Wasm 优秀文档](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/Using_the_JavaScript_API#preparing_the_example)（developer.mozilla.org）的例子，展示 Wasm 如何调用 `console.log`。虽然 Wasm 的主要格式是二进制字节码，但规范还定义了一种文本格式，称为 WAT（Wasm 文本），可以很容易地了解其中的原理：

```
(module
	(func $log (import "myConsole" "myLog") (param i32))
	(func (export "log42")
		i32.const 42
		call $log))
```

Wasm 是一种模块语言：每个 Wasm 模块声明导入和导出。要运行模块，你需要用一组导入来*实例化*它，这个操作会提供一组导出。Wasm JavaScript API 使这种模块实例化功能可以从 JavaScript 访问。

这个例子是一个简单的模块，它从模块 `myConsole` 中导入一个名为 `myLog` 的函数。它导出一个函数 `log42`，该函数用参数 `42` 调用 `myLog`。JavaScript 代码可以通过引用全局对象来调用任何 Web API，但 Wasm 只能访问你提供给它的内容，因此 `console.log` 通过模块导入传递给 Wasm：

```js
const importObject = {
    myConsole: {
        myLog(arg) {
            console.log(arg);
        }
    }
};
const { instance } = await WebAssembly.instantiateStreaming(
    fetch("simple.wasm"),
    importObject
);
instance.exports.log42();
```

其思想是，为网站输出 Wasm 的构建工具链实际上会输出 Wasm 和 JavaScript 的组合，后者负责加载模块并将其与适当的 JavaScript 功能（如这个 `myConsole` 模块）链接起来。

 

### 用平面内存建模一切

套用德国数学家利奥波德·克罗内克的话：上帝创造了 `i32`、`i64`、`f32` 和 `f64`；其余的都是人类的杰作。

WebAssembly 从一个简单的内置类型系统开始。就可以在栈上存在并作为函数参数传递的值而言，它最初只支持适合其平面位图内存的类型：即前面提到的四种字节可寻址的数值类型。
然而，事实证明，这使得 Wasm 字节码完全能够调用 JavaScript API，即使是那些接受对象作为参数的 API，而不仅仅是像 `console.log` 示例中那样的数字。

实现方法如下：

1. 在 JavaScript 中维护一个数组，包含 Wasm 程序需要关注的所有 JavaScript 对象引用。
2. JavaScript 导出到 Wasm 的模块被包装起来。当一个函数需要接受对象作为参数并返回不同对象时，包装器将接受并返回该数组的整数索引，并为返回值分配一个新条目。
3. Wasm 代码在不再需要这些引用时，会调用另一个从 JavaScript 导入的函数来显式释放它们，该函数管理一个空闲列表。
4. 最终的产物是 JavaScript 和 Wasm 的捆绑包，而不仅仅是 Wasm。

"这是作弊，"我听到你抗议道。"这不是 Wasm，这只是一个复杂的 JavaScript 装置，中间夹杂了一点 Wasm！"也许是这样，但引导 Wasm 项目启动一直是这样计划的，而且它仍然允许你用 Wasm 编写核心逻辑。

这种极简设计借鉴了 asm.js 的成功经验。它还借鉴了 [Chrome 的 NaCl（Native Client）项目](https://web.archive.org/web/20200322130342/https:/developer.chrome.com/native-client/overview)（web.archive.org）的使命，NaCl 引入了新的 Pepper 系统来进行 I/O，但没有得到跨浏览器支持。（NaCl 现在已经被弃用，其文档页面是 404，所以你需要访问互联网档案馆才能了解它）。

这一切都回到了 Wasm 的原始目标：让更多程序能够在 Web 上以良好的性能运行，而不是消除最后一点 JavaScript。程序的核心编译为 Wasm 可能是最重要的优化部分，这取决于用 JavaScript 编写时它会有多慢或多臃肿。
用 Wasm 而不是 JavaScript 交付这个核心可能是让应用实际工作的关键。一点边缘 JavaScript 并不会否定这种好处。

这种设计的核心思想是，Wasm 是用编译器工具链构建的，能够在 JavaScript/Wasm 边界建立约定并生成匹配的代码。已经创建了许多这样的编译器工具链并广泛使用，包括 [C/C++](https://emscripten.org/)（emscripten.org）、[Rust](https://rustwasm.github.io/docs/book/)（rustwasm.github.io）、[Kotlin](https://kotlinlang.org/docs/wasm-overview.html)（kotlinlang.org）、[Java](https://developer.fermyon.com/wasm-languages/java)（developer.fermion.com）等。每一种都以这种方式将 Web API 连接到 Wasm，因此应用开发者无需担心。

 

### 先苦后甜

如果你仔细想想，你基本上可以用这种混合的 JavaScript/Wasm 设计来建模一切。以下是一些已在实际 Wasm 构建工具链中实现的例子。

 

#### 异常处理

调用导入的 JavaScript 函数来抛出异常（还不算太糟）并建模 try/catch 块（这就相当糟糕了）：

- 将 Wasm 函数导出到 JavaScript 中的每个内部块。
- 在 JavaScript 中执行 try/catch。
- 然后将整个组合好的函数导出回 Wasm。

 

#### 阻塞 I/O

许多你可能想编译成 Wasm 的程序都是用同步阻塞行为编写的，但 JavaScript（以及更广泛的 Web 平台）是非阻塞的，而是基于 JavaScript 运行完成而不等待 I/O，稍后通过 Promise 和回调跟进。
有两种方案可以桥接这些模型：

- 在主线程外运行 Wasm，在 Web Worker 中它可以阻塞。使用由 JavaScript SharedArrayBuffer 支持的 Wasm 内存与主线程通信。
- 为了让计算能够暂停并稍后恢复，基于延续传递风格转换显式表示部分调用栈，使用某种分析来确定程序中可能阻塞的点。

 

#### 垃圾回收值

在要编译到 Wasm 的语言中，有两种选择：

- 将自己的 GC（垃圾收集器）编译到 Wasm 中，在其平面内存上运行。
  这需要维护一个并行的"影子栈"根（开始遍历对象图的活动值），因为 Wasm 不允许用户空间 GC 查看栈以找到其根。
- 调用 JavaScript 来分配值和访问属性；一切都使用普通 JavaScript 对象。

尽管你*可以*用 Wasm 最初的最小功能来表达一切，但 Wasm 的全部意义在于通过减少间接性来让应用运行得更快。现在我们只是在增加更多间接性！
例如，前面描述的异常处理方案被发现在移植到 Wasm 的 C++ 程序中造成了很大的性能下降。

 

### 情况会好转

关键是不要优先考虑"什么能让我完全用 Wasm 而不是 JavaScript 完成所有事情"，而是优先考虑"什么能让我的程序实际工作得更好"，转而关注那些在性能或代码大小方面实际使用中特别麻烦的部分。
此外，策略是逐步工作，一点一点地添加功能，同时记住更大的整体构想。

有时，实现可以透明地提高性能。例如：

- 优化 [Wasm 和 JavaScript 之间的调用](https://hacks.mozilla.org/2018/10/calls-between-javascript-and-webassembly-are-finally-fast-🎉/)（hacks.mozilla.org），包括构建步骤生成的代码
- 引入 [多层 JIT（即时）编译器](https://v8.dev/docs/wasm-compilation-pipeline)（v8.dev），其中 [更多精力用于优化](https://spidermonkey.dev/blog/2024/10/16/75x-faster-optimizing-the-ion-compiler-backend.html)（spidermonkey.dev）频繁运行的代码
- 在某些条件下，在优化 JIT 中 [在 Wasm 和 JavaScript 之间内联](https://chromium.googlesource.com/v8/v8.git/+/refs/heads/main/src/compiler/wasm-inlining-into-js.cc)（chromium.googlesource.com）

然而，其他时候，Wasm 需要添加全新的功能来消除某些类型的开销。这些功能包括异常、阻塞操作和垃圾回收值的支持。

 

#### 异常处理

功能包括原生异常 [在 Wasm 中抛出和 try/catch](https://github.com/WebAssembly/exception-handling/blob/main/proposals/exception-handling/Exceptions.md)（github.com）。

 

#### 阻塞操作

WebAssembly 具有 [暂停执行](https://v8.dev/blog/jspi)（v8.dev）以等待 JavaScript Promise 的原生能力。

 

#### 垃圾回收值

一系列针对不同支持部分的添加都基于共享 JavaScript 堆的想法，而不是鼓励将其他 GC 编译到 Wasm 中：

- 在栈和全局中引用 JavaScript [值](https://github.com/WebAssembly/reference-types/blob/master/proposals/reference-types/Overview.md)（github.com），无需那个有趣的额外数组
- 分配和访问 [垃圾回收结构和数组](https://github.com/WebAssembly/gc/blob/main/proposals/gc/Overview.md)（github.com），无需进入 JavaScript 或产生 JavaScript DOM 的开销
- 直接处理 JavaScript 字符串，使它们 [无需在 JavaScript 和 Wasm 堆之间复制](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/JavaScript_builtins)
- JavaScript 中的终结器允许 Wasm 程序在 JavaScript 代码不再使用某个值时 [清理其底层线性内存](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/FinalizationRegistry)（developer.mozilla.org），因为你无法说服 JavaScript 开发者一致地调用 `free()`

 

#### 好消息

至少在最新的实现中，Wasm 已经添加了 [这些功能](https://web.dev/blog/wasmgc-wasm-tail-call-optimizations-baseline)（web.dev）。
虽然这些功能都不能让你无需任何胶水代码访问 DOM，但它们确实显著提高了可能想要与 DOM 交互的代码性能：现代、功能丰富的垃圾回收语言是大多数 UI 和新代码的构建之处。

 

### 但是直接 DOM 访问呢？

长期以来，Wasm 组件模型被讨论为更直接访问 Web API 的可能途径。事实上，组件模型的早期草案被称为"[Web IDL 绑定](https://github.com/WebAssembly/interface-types/blob/c4cb0a71253ea355b3f4bd5aa54edc6387e0d3ab/proposals/webidl-bindings/Explainer.md)"（github.com）。

[Web IDL（接口描述语言）](https://webidl.spec.whatwg.org/)（webidl.spec.whatwg.org）基于 [OMG（对象管理组）IDL](https://www.omg.org/spec/CORBA/2.3.1)（omg.org），是 CORBA（公共对象请求代理体系结构）的一部分。Web IDL 被分叉以确保 Web API 能够精确地指定它们在 JavaScript 中的工作方式，而 CORBA 没有定义 JavaScript 映射。
像 OMG IDL 一样，Web IDL 最初是一种跨语言机制，不仅支持 JavaScript，还支持 Java——记住，在早期，Mozilla 正在开发基于 Java 的 Web 浏览器，Java 小程序最初被期望成为 Web 的重要组成部分。
Web IDL 公开的 API 实现往往用 C++ 或 Rust 编写。考虑到这种跨语言特性，Web IDL 会是 Wasm 绑定的良好基础吗？

 

### Web API 是 JavaScript API

将 Web IDL 与 JavaScript 分离并不那么简单。
Web IDL 多年前就放弃了 Java 支持，以便更灵活地发展，支持更多"JavaScript 风格"的 API，包括迭代器、Promise、命名空间等，这些在 Java 端很难给出匹配的解释。
要真正提取 Web IDL 中的 JavaScript 部分并设计更直接的 Wasm 映射，需要深入思考。

所有现代 Web 浏览器都基于 API 的 Web IDL 定义，使用代码生成来实现大多数 Web IDL 公开的 API，确保行为一致正确。那么，只需调整这个脚本以生成一些额外的 Wasm 绑定，对吧？
没那么快——有几个问题：

- 首先，这些生成器是几千行代码的大型脚本，大多是很久以前编写的，很难修改。
- 其次，浏览器源代码库中的 Web IDL 往往与源规范有细微差别。这样做是为了指导代码生成器处理一些更精细的方面。
  为 Wasm 定义映射需要检查所有这些差异，看看哪些可能需要改回以确保一致性——错误的更改可能会破坏某些网站。

并非所有 Web API 都使用 Web IDL。例如，JavaScript 规范本身并未在 Web IDL 中定义其标准库。
Ecma International 的 TC39（JavaScript 标准委员会）曾考虑采用 IDL，但考虑到应用的约定存在各种不匹配，更不用说对现有 JavaScript 功能进行任何可观察的更改所带来的兼容性风险，这并非易事。

话虽如此，某些 JavaScript 功能在 Wasm 程序中肯定会有用。此外，一些 Web IDL 定义的 API 不是用标准 Web IDL 生成器实现的。
在大多数实现中，Wasm/JavaScript API 本身不使用此生成器，因为它是在 JavaScript 引擎而非浏览器层中实现的。

总而言之，将当今的 Web API（包括 DOM）视为 JavaScript 原生的，而不是跨语言的，更为准确。

 

#### Wasm 组件模型怎么样？

If we can work through all of that, web APIs could be exposed as Wasm modules, perhaps in a manner similar to the built-in support for JavaScript strings described earlier. But rather than modules that work just one way, it might be more efficient to use the Wasm Component Model.

Different programming languages use different sorts of memory layouts (e.g., strings in linear vs. GC memory).
To get the best speedups, you would want to target the most appropriate one directly, rather than doing an extra copy in some cases—this is part of what the Component Model provides.
Web API imports via Web IDL and the Component Model are prototyped as part of the Jco project, which brings [the Wasm Component Model to JavaScript](https://bytecodealliance.github.io/jco/transpiling.html#experimental-webidl-imports) (bytecodealliance.github.io).

Would this feature actually improve runtime performance or size of distributed applications? While there would probably be some size reduction in terms of less JavaScript glue code generated, it's unclear if it's enough to matter.
Additional prototyping would be needed to find out what sorts of benefits would actually be gained in practice.

For now, web folks don't seem to be sold on the urgency of this very large project. There is no active work by browser vendors in this direction.
The plan is to give the Component Model effort, led more by server folks, some time to develop, and maybe later see if something useful emerges from that.

One possible future, under development as part of Jco, is for the Component Model and any components representing web APIs to be more of a toolchain convention rather than something built into browsers.
In this form, toolchains would have less work to do, relying on shared components to access web APIs/DOM instead of needing to roll their own bindings. When the rubber hits the road, this strategy would mean that you're still going through JavaScript.

### Evolving the Wasm Bytecode Format

Like many programming languages, Wasm is developed in a *standards committee*, a group of experts from different backgrounds who come together to design, debate, prototype, and document new additions to the bytecode.

This standards committee is the W3C Wasm Community Group. As the name suggests, it's part of the World Wide Web Consortium (W3C). "Community Group" indicates that this group is open to the whole developer community.
Anyone can sign onto the intellectual property policy and start contributing to this group without paying a W3C membership fee.

Still, that doesn't mean that you can just join and push something through single-handedly.
Standards work is about consensus building, which means you need to repeatedly justify the feature's utility and design to various audiences in various ways until (almost) everyone is on board with the idea.
It's especially important either to prototype the feature yourself—or to persuade others to do so—early in the process. To make decisions, the Wasm CG uses [a lightweight voting process](https://github.com/WebAssembly/meetings/blob/main/process/consensus.md#formal-consensus-at-meetings) (github.com) that amounts to [rough consensus](https://en.wikipedia.org/wiki/Rough_consensus) (wikipedia.org).

To facilitate incremental development and prototyping in alignment with the CG, there is [a six-phase process](https://github.com/WebAssembly/meetings/blob/main/process/phases.md) (github.com), inspired in part by [TC39's stages](https://tc39.es/process-document/) (tc39.es). The idea is to interleave design, prototype implementations, and consensus building.
This way, the group can learn from experience before declaring a standard "final," while enabling draft implementations to be increasingly aligned with the direction of the group as they become increasingly advanced.

Input from different parties is important for developing a good Wasm feature. These different parties include:

- Wasm engine maintainers, including engines that run in web browsers, to make sure a feature can be implemented
- Build toolchain maintainers*,* to make sure the feature will be feasible and useful to output as part of a build process
- Developers of applications using Wasm, to assess the overall impact of proposed features and their usability as exposed by toolchains
- Academic researchers*,* to apply decades of related research to inform the design of features, and to think through the details of formal definitions, identifying issues and ensuring the resulting standard is sound and not ambiguous

If you're in one of these groups, please contribute to the Wasm CG by giving feedback in [GitHub's issues for proposal repositories](https://github.com/WebAssembly/exception-handling/blob/main/proposals/exception-handling/Exceptions.md) (github.com) and by joining [the Wasm CG's regular meetings](https://github.com/WebAssembly/meetings) (github.com). You can join the Wasm CG via its [W3C website](https://www.w3.org/community/webassembly/) (w3.org).

 

### Is Wasm Complete?

There are still ways to further reduce the overhead of programs that span the JavaScript/Wasm boundary, including:

- Runtime type metadata. When Wasm/JavaScript engines allocate the structs the Wasm GC provides, the Wasm engine ends up needing a pointer in the header of the object to type-level metadata (e.g., to allow tracing by GC and type checking at the JavaScript/Wasm boundary).
  Native implementations of programming languages such as JavaScript and Java tend to use such an analogous header pointer to link to other language-level metadata (e.g., the table of methods).
  With the initial capabilities of Wasm GC, however, an additional struct field must be used.
  The capability to combine this metadata into one pointer per instance is proposed to be exposed to Wasm in a way that should make performance better in practice simply by avoiding the need for both that extra word of memory (when an object is used just within Wasm) and [wrapper objects](https://github.com/WebAssembly/custom-descriptors) (to expose things ergonomically to JavaScript) (github.com).
- It's common for JavaScript APIs to accept arguments that must be of a particular type, enforced via a runtime type check. For example, this check is needed for the functionality to work with JavaScript strings, and DOM methods also similarly need to check their parameters.
  If Wasm's type system models these objects as generic pointers to JavaScript objects rather than a more specific type, then a runtime type check is needed when the APIs are invoked from Wasm as well.
  It would be great if Wasm's type system could prove statically that the check can be omitted. One proposed solution is type imports: the ability to import a type from another module. This would play one small role in reducing the overhead of [calling from Wasm into the DOM](https://github.com/WebAssembly/memory-control/blob/main/proposals/memory-control/Overview.md) (github.com), but it hasn't been prioritized since these type checks are already pretty fast.

There's more than that going on in the Wasm CG; for example, this author is particularly excited about the [memory control proposal](https://github.com/webassembly/memory-control/blob/main/proposals/memory-control/Overview.md) (github.com), which could significantly improve security by making dereferencing a null pointer throw, which has been found to be [a security issue](https://www.usenix.org/conference/usenixsecurity20/presentation/lehmann) (usenix.org). See also, "[On Binary Security of Wasm](https://www.wingolog.org/archives/2020/10/15/on-binary-security-of-webassembly)" (wingolog.org).

For each of these features, as well as direct DOM/web API access, browser vendors will decide whether to implement the feature based on whether it improves actual performance or code size.
Otherwise, the tools to integrate Wasm into web applications are already there and are being successfully applied.

 

### Where Wasm Fits In

What should be relevant for working software developers is not, "Can I write pure Wasm and have direct access to the DOM while avoiding touching any JavaScript ever?" Instead, the question should be, "Can I build my C#/Go/Python library/app into my website so it runs with good performance?" Nobody is going to want to write that bytecode directly, even if some utilities are added to make it easier to access the DOM.

WebAssembly should ideally be an implementation detail that developers don't have to think about.
While this isn't quite the case today—JavaScript stubbornly maintains a leg up as something that "Just Works," with web APIs and developer tools designed primarily against it, and JavaScript build toolchains acting as merely an optimization—the thesis of Wasm is, and must be, that it's okay to have a build step.

For the foreseeable future, when this build step is used to deploy Wasm on the web, the build output will have both JavaScript and Wasm.
