# What is Module Federation?

Module Federation is a powerful feature introduced in **Webpack 5** that allows JavaScript applications to **load code** from another application **at runtime dynamically**. This lets you share modules between applications without bundling them together at build time.

Think of it as “lazy loading a remote app”. It supports true **micro-frontend architecture**, where each part of the application can be:

- Developed independently
- Deployed independently
- Shared seamlessly

# The Problem It Solves

Before Module Federation:

- Front-end monoliths grow big and slow.
- Sharing code between apps meant creating and maintaining libraries.
- Multiple teams working on the same repo led to merge hell and deployment bottlenecks.

With Module Federation:

- Teams build, test, and deploy independently.
- Shared dependencies are loaded only once.
- You can integrate or split codebases gradually.

# How Vite Supports Module Federation

Vite does not support Module Federation natively like Webpack. However, the amazing `vite-plugin-federation` brings the same capabilities to Vite apps.

# Architecture Diagram

```
+--------------------+         +-------------------+         +-------------------+
  |    Host App        |  <--->  |  Remote App A     |  <--->  |  Remote App B     |
  | (Dashboard)        |         | (User Profile)    |         | (Notifications)   |
  +--------------------+         +-------------------+         +-------------------+
         |                                    |                             |
         |        Dynamically loads exposed modules at runtime              |
         +-------------------------------------------------------------------+
```

Each app has its own build & deploy pipeline but works together seamlessly at runtime.

# Real-World Example with Vite

Let’s build a **host app** called `dashboard` and a **remote app** called `user-profile`.

# 1. Remote App: `user-profile`

## Setup

```
npm create vite@latest user-profile -- --template react
cd user-profile
npm install
npm install vite-plugin-federation
```

## vite.config.js

```
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import federation from '@originjs/vite-plugin-federation';

export default defineConfig({
  plugins: [
    react(),
    federation({
      name: 'user_profile',
      filename: 'remoteEntry.js',
      exposes: {
        './UserProfile': './src/UserProfile.jsx'
      },
      shared: ['react', 'react-dom']
    })
  ],
  build: {
    target: 'esnext',
    minify: false,
    cssCodeSplit: false
  }
});
```

## src/UserProfile.jsx

```
export default function UserProfile() {
  return <div>User Profile Component from Remote</div>;
}
```

## Run Server

```
npm run dev -- --port 5001
```

# 3. Host App: `dashboard`

## Setup

```
npm create vite@latest dashboard -- --template react
cd dashboard
npm install
npm install vite-plugin-federation
```

## vite.config.js

```
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import federation from '@originjs/vite-plugin-federation';

export default defineConfig({
  plugins: [
    react(),
    federation({
      name: 'dashboard',
      remotes: {
        user_profile: 'http://localhost:5001/assets/remoteEntry.js',
        notifications: 'http://localhost:5002/assets/remoteEntry.js'
      },
      shared: ['react', 'react-dom']
    })
  ],
  build: {
    target: 'esnext',
    minify: false,
    cssCodeSplit: false
  }
});
```

## src/App.jsx

```
import { lazy, Suspense } from 'react';

const UserProfile = lazy(() => import('user_profile/UserProfile'));
const Notifications = lazy(() => import('notifications/Notifications'));
function App() {
  return (
    <div>
      <h1>Dashboard</h1>
      <Suspense fallback={<div>Loading Profile...</div>}>
        <UserProfile />
      </Suspense>
      <Suspense fallback={<div>Loading Notifications...</div>}>
        <Notifications />
      </Suspense>
    </div>
  );
}
export default App;
```

## Run Server

```
npm run dev -- --port 5000
```

Now visit `http://localhost:5000` and see both `UserProfile` and `Notifications` rendered.

# Advanced Concepts

# 1. Shared Libraries

Avoid loading the same library multiple times:

```
shared: {
  react: { singleton: true, requiredVersion: '^18.0.0' },
  'react-dom': { singleton: true }
}
```

- **singleton** ensures the app uses only one instance.
- **requiredVersion** can help avoid version mismatches.

# 2. Dynamic Remotes

Sometimes, remote URLs come from an API or config:

```
remotes: {
  notifications: () => `Promise.resolve(window.remoteNotificationUrl)`
}
```

Inject this `window.remoteNotificationUrl` dynamically in your HTML or runtime config.

# 3. Lazy Import with Error Boundary

To gracefully handle remote load failures:

```
import { lazy, Suspense } from 'react';

const RemoteComponent = lazy(() => import('remote_app/Component'));
function ErrorBoundary({ children }) {
  try {
    return children;
  } catch (err) {
    return <div>⚠️ Failed to load module</div>;
  }
}
function App() {
  return (
    <ErrorBoundary>
      <Suspense fallback={<div>Loading...</div>}>
        <RemoteComponent />
      </Suspense>
    </ErrorBoundary>
  );
}
```

# 4. Exposing Multiple Modules

```
exposes: {
  './ComponentA': './src/ComponentA.jsx',
  './ComponentB': './src/ComponentB.jsx'
}
```

This lets the host selectively import only what it needs.

# 5. Version Mismatch Handling Between Host & Remote

You can control **what version** of a dependency a host app accepts when sharing:

```
shared: {
  react: {
    singleton: true,
    strictVersion: true,
    requiredVersion: '^18.2.0',
  },
}
```

- **strictVersion**: true ensures that a remote will not be loaded if it doesn’t match.
- Use fallback mechanisms or version negotiation when building highly distributed systems.

# 6. Fallback UI or Modules for Offline or Failure Scenarios

Sometimes, a remote might be unavailable (e.g., during deployment). In such cases:

```
const Notifications = lazy(() =>
  import('notifications/Notifications')
    .catch(() => import('./local/NotificationsFallback'))
);
```

# 7. Cross-Framework Federation

You can federate between different frameworks (e.g., React host + Vue remote):

- Use wrappers to mount/unmount Vue components in React.
- Prefer exposing native Web Components from the remote.

# 8. Scoped Styling Across Federated Apps

Federated apps can cause style collisions. Solutions:

- Use **CSS Modules**, **Scoped SCSS**, or **Shadow DOM**.
- Namespace classNames in each remote app.

# 9. Federated Routing

If each remote app has its own routes, set up a central router in the host:

```
<Route path="/user" element={<UserProfile />} />
<Route path="/notifications" element={<Notifications />} />
```

You can also let remotes export routes themselves and dynamically mount them into a central router config.

# 10. Federated State Sharing (Advanced)

Avoid tight coupling for state. But if needed, use tools like:

- A shared Redux store exposed via Module Federation
- Context API shared as singleton
- Pub/Sub system (like eventemitter3, or browser-native CustomEvent)

# Deployment Best Practices

- Deploy each app on a unique subdomain or port.
- Ensure `remoteEntry.js` is cache-busted using hashed filenames.
- Use environment variables or config maps to inject remote URLs.
- Automate contract testing between the host and remotes.

# When to Use Module Federation

**Perfect for:**

- Enterprise-scale applications
- Teams working in parallel
- Apps needing runtime plugin-like behaviour

**Avoid if:**

- You’re building a small/medium app with a single team
- Deployment complexity outweighs benefits
